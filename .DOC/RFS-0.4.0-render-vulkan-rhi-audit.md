# RFS-0.4.0 — разбор рендера, Vulkan и RHI

Аудит коммита `de483a9`. Всё ниже проверено на коде и, где возможно, на сборке.
Не пересказ документации проекта — там местами она расходится с кодом, и это
отмечено отдельно.

## 0. Что это за проект, если убрать маркетинг

`rfs-client` — **библиотека**. Не приложение.

В `Cargo.toml` нет ни `[[bin]]`, ни `src/main.rs`. Единственные исполняемые
артефакты — четыре примера в `examples/`, один из которых не компилируется
(см. §2.1). Ни одного игрового бинаря в репозитории нет.

Масштаб (пересчитал, не по верхней границе списка):

| Слой | Строк | Тестов |
|---|---:|---:|
| `src/rhi` | 21 353 | 140 |
| `src/render` | 20 505 | **15** |
| `server_src` | 19 510 | 120 |
| `Tool/client_tests` | 12 910 | 690 |
| **Всего** | **75 086** | **965** |

Распределение тестов — самый честный индикатор зрелости: **690 тестов в тест-харнессе

от GPU.

## 1. Главный вывод

Движок в статусе **«один работающий пасс в пустоте»**.

Единственный геометрический вызов отрисовки во всём `src/render/**` — это
`Command::DrawIndexed` в `src/render/passes/geometry.rs:668`. Плюс
`draw_indexed_instanced` в частицах (`src/render/particles/system.rs:201`) и
прямоугольники UI. Всё.

Что делают остальные пассы:

| Пасс | Что реально делает `execute()` |
|---|---|
| `gbuffer.rs` | `begin_render_pass` → очистка 5 аттачментов → `end`. **Нет ни одного draw.** |
| `lighting.rs` | `begin` → цикл `bind_texture(view, 0)` по всем ресурсам → `end`. **Нет draw.** |
| `shadow.rs` | `begin`/`end` на каждый каскад. Ничего не рендерит в карты теней. |
| `transparent.rs` | Сортирует объекты в `Vec`… и сортированный `Vec` ни разу не используется для отрисовки. |
| `water.rs` | `begin`/`end`, опционально bind пайплайна. Дальше — заглушки. |
| `postprocess/*` | 5 эффектов, все — pass-through `copy_texture` или no-op. |

Проект **сам это признаёт** — `BUGS.md`, Баг№186: *«ОСТАЁТСЯ: … `RenderPassNode::execute`
большинства пассов остаётся заглушкой без реальных GPU/shader-команд»*.

Проверил сам: `grep` по draw-вызовам в `src/render/**` даёт ровно одно совпадение.
Заявление соответствует коду.

### 1.1. Пасс, который работает, — сирота

`Renderer::initialize()` (`src/render/core/renderer.rs:227`) вызывает
`render_graph.initialize()`, который добавляет **только ресурсы** — ни одного пасса
(`src/render/graph/graph.rs:67-75`). Комментарий на `renderer.rs:184-186` признаёт
это прямо: *«`add_pass` не имеет вызывающего кода»*.

Все вызовы `add_pass` в репозитории:

- `examples/cube.rs:131` — единственный в продуктовом коде
- остальные 9 — в `Tool/client_tests/tests/*`

**Итог:** собранный рендер-граф из 20 500 строк не создаёт ни одного пасса по
умолчанию. Чтобы получить картинку, нужно руками собрать граф в примере.

### 1.2. Шейдеры — и вот это по-настоящему больно

- В продуктовых `assets/shaders/` лежат **8 файлов `.wgsl` и ноль `.spv`**.
- `VulkanLogicalDeviceResource::create_shader_module` принимает **исключительно
  SPIR-V** и возвращает `NotSupported` на что-либо ещё
  (`src/rhi/backend/vulkan/device.rs:1067-1072`).
- Компилятора WGSL→SPIR-V в графе зависимостей **нет**. Ни `naga`, ни `shaderc`,
  ни `glslang`. Единственная реализация трейта `ShaderCompiler` — `StubShaderCompiler`
  (`src/rhi/shader/compiler.rs:53`), которая кладёт исходный текст в байты и
  возвращает пустой reflection. Её doc-комментарий — *«для CPU-only сборок
  клиента»* — устарел: настоящий Vulkan-бэкенд уже есть.
- `naga` подключён **только как dev-зависимость тест-харнесса**, с комментарием
  (`Tool/client_tests/tests/compile_shaders.rs:3`): *«пользователь решил не переносить
  `naga` в крейт `rhi`»*.

И文化culatorка, от которой у меня холодок:

```rust
// examples/cube.rs:32-33
//! Compiled from `Tool/client_tests/assets/shaders/geometry.wgsl` by
//! `cargo test -p client_tests --test compile_shaders -- --ignored`.
const SHADER: &[u8] = include_bytes!("../Tool/client_tests/assets/shaders/geometry.spv");
```

**Единственный пример, который рисует настоящую геометрию, берёт скомпилированный
шейдер из assets тестового харнесса.** Продукт не умеет ни собрать шейдер, ни
прочитать свои собственные 8 `.wgsl`.

## 3. RHI — слой абстракции

### 3.1. Три из четырёх бэкендов — пустышки, и их код вообще не компилируется

`Cargo.toml` объявляет `default = ["vulkan", "d3d12", "d3d11", "opengl"]`.
По факту:

- `d3d12/mod.rs`, `d3d11/mod.rs`, `opengl/mod.rs` — каждый 34 строки, все три
  метода возвращают `RhiError::NotSupported("... is a stub without a real GPU API")`.
- Их `device.rs` (**654 + 523 + 519 = 1696 строк**) **не подключены ни одним
  `mod device;`** — ни в одном из трёх `mod.rs`. Файлы не компилируются вообще.

Проверил системно — скриптом по всем 279 `.rs`: не подключены 6 файлов.

```
backend/vulkan/pipeline_cache.rs   ← не подключён
prelude.rs                         ← не подключён
ui/theme.rs                        ← не подключён
backend/{d3d11,d3d12,opengl}/device.rs ← не подключены
```

`prelude.rs` — вдвойне мёртвый: он ссылается на `crate::rhi::Rhi`, а такого
модуля в крейте `rhi` нет. Он не скомпилировался бы, даже будь подключён.

При этом `lib.rs` обещает:

> Supported APIs: Vulkan 1.3 (Primary), Direct3D 12, Direct3D 11, OpenGL 4.6
> Modern rendering (Ray Tracing, Mesh Shading, VRS, Bindless)

Из этого списка работает один пункт.

### 3.2. Мёртвый код, который выглядит как работающая фича

**Pipeline cache.** `src/rhi/backend/vulkan/pipeline_cache.rs` — 76 строк с
документацией «Improves pipeline creation performance by caching compiled
pipelines». Не подключён к модулю. Оба места создания пайплайнов передают
`vk::PipelineCache::null()` (`device.rs:1339`, `device.rs:2029`).

**Следствие:** каждый `create_graphics_pipelines` компилирует шейдеры из SPIR-V в
ISA заново, и кэш не переживает перезапуск процесса. Для 8 пассов при старте это
десятки-сотни миллисекунд на каждом запуске. Классическая задача на полчаса
работы, не сделанная.

**Память: 1158 строк в никуда.** `src/rhi/memory/` — `buddy.rs` (368),
`pool.rs` (455), `linear.rs` (216), `heap.rs`, `budget.rs`, `allocator.rs`.
Проверил: `BuddyAllocator`, `LinearAllocator`, `MemoryPool`, `MemoryHeap` и трейт
`MemoryAllocator` **не используются нигде за пределами своего модуля**. Сам
`memory/allocator.rs` помечен `TODO: Full implementation required`.

Vulkan-бэкенд использует completely отдельный, наивный `backend/vulkan/memory.rs`.

### 3.3. Дизайн RHI, который работает

Честно — здесь сделано грамотно:

- **Владение ресурсами вынесено из value-типов в `VulkanLogicalDeviceResource`**
  (`tracked: Mutex<Vec<TrackedObject>>`). Правильное решение: `GpuResource`
  копируется по значству в `Texture`/`Buffer`/`TextureView` и свободно клонируется,
  деструктор на уровне value-типа дал бы двойной free. Их же объяснение в коде
  верное.
- **Порядок teardown по зависимостям, а не по возрасту** (`TEARDOWN_ORDER`,
  `device.rs:351`) — с описанием, почему обход назад давал `STATUS_ACCESS_VIOLATION`.
  Это правильно, и это редкость.
- **`flush`/`invalidate` через `VK_WHOLE_SIZE`** с корректным объяснением про
  `nonCoherentAtomSize`. Правильное решение для аллокатора, дающего каждому
  аллокату свой `VkDeviceMemory`.
- **Выбор memory type с приоритетом coherent** (`select_memory_type`) — покрыт
  шестью тестами, включая регрессию на «не деградировать молча».
- `139/140` тестов RHI проходят, clippy чист.

## 4. Vulkan-бэкенд

### 4.1. 🔴 Баг №282: презентация не синхронизирована, и авторы это знают

Это самое важное в бэкенде, и оно **не исправлено**.

```rust
// src/render/core/renderer.rs:346
let render_finished = crate::rhi::ash::vk::Semaphore::null();
```

`vkQueuePresentKHR` вызывается с `wait_semaphore_count = 0`. Между «кадр
отправлен» и «образ освобождён» нет ни одной сигнальной связи на уровне GPU.

`arm_presentation_signal()` — **мёртвый код**. Проверил: функция определена в
`rhi/core/device.rs:481` и в трейте бэкенда, но **не вызывается нигде в
репозитории**. Инфраструктура семафора построена, отлажена, задокументирована и
отключена.

Честно — в реестре это записано без прикрас (`BUGS.md`, Баг№282):

> **НЕ ИСПРАВЛЕНО**, и важно зафиксировать ПОЧЕМУ, потому что я попытался и
> откатил. … С отключённым сигналом индекс застревал на 0, то есть стало хуже
> прежнего (`0 -> 2 -> 2`). Эксперимент откачен, чтобы не оставить регрессию с
> валидационной ошибкой каждый кадр; инфраструктура оставлена и компилируется,
> но не используется.

С доказательством из слоя валидации: `VUID-vkQueueSubmit-pSignalSemaphores-00067`.
Диагноз верный — один семафор на все кадры действительно нельзя переиспользовать,
пока `queue_present` не забрал предыдущий. Лечение они назвали правильно: кольцо
кадров в полёте.

**Оценка:** дефект задокументирован образцово, но он не в списке «109 не
исправленных, которые надо закрыть» — он в коде как «решено», потому что
инфраструктура есть. Кто-то, читая репозиторий, увидит `render_finished`,
`arm_presentation_signal`, `submit_recorded_signalling` и решит, что синхронизация
есть.

### 4.2. 🔴 Полное отсутствие конвейера — жёсткий потолок производительности

`submit_recorded` (`device.rs:516`) на каждом сабмите:

```rust
self.device.wait_for_fences(&[self.submit_fence], true, u64::MAX)
```

Один command buffer, один command pool, один fence, `submit_lock` на всё окно
записи. Плюс `acquire` ждёт свой fence (`present.rs:352`).

Кадр выглядит так:

```
acquire (блок) → запись → submit → БЛОК на fence до упора → present
```

CPU и GPU **никогда не работают одновременно**. Перекрытия нет физически.
Чтобы вырасти, нужно кольцо кадров в полёте — то самое, что они написали в
качестве условия для №282. Один и тот же блокер на два пункта: корректность
презентации и производительность.

Их комментарий на `present.rs:177` — *«One image beyond the minimum so the CPU
can prepare the next frame while the GPU finishes the current one»* — **не
соответствует коду**: CPU никогда не готовит следующий кадр, пока текущий не
закончен. `image_count = min + 1` не даёт ничего.

### 4.3. 🔴 Один `VkDescriptorPool` на каждый `DescriptorSet`

```rust
// device.rs:1154-1160
let pool_info = vk::DescriptorPoolCreateInfo {
    max_sets: 1,   // ← пул на один сет
    ...
};
```

Создание одного сета = создание пула. Уничтожение пула = уничтожение сета.
На каждое перебиндингование — создание и удаление объекта Vulkan.

Это один из самых дорогих вызовов в API (внутренние блокировки драйвера,
реконструкция таблиц). Считается на каждый кадр, если сеты пер-фреймовые.
Каноническое решение — переиспользуемый пул + `allocate` + `reset` или ring
с кольцевыми аллокациями. У них уже есть `descriptor/allocator.rs` — проверьте,
прежде чем писать новое.

### 4.4. 🟡 Аллокатор памяти упирается в лимит

Каждое выделение = отдельный `vk::DeviceMemory` (`backend/vulkan/memory.rs`).
`VkPhysicalDeviceLimits::maxMemoryAllocationCount` на десктопных GPU — **4096**.

Для морского боя с моделями, частицами, UI и рендер-таргетами 4096 отдельных
аллокаций — это потолок, в который упрётся игра среднего размера. Их
`buddy.rs`/`pool.rs` (823 строки) написаны и не подключены (§3.2). Это ровно тот
случай, когда «минимальный» аллокатор стоит дороже, чем его отсутствие.

### 4.5. 🟡 Формат поверхности выбирается перебором

`pick_surface_format` (`present.rs:478`) ищет `B8G8R8A8_SRGB` и, если не находит,
берёт `formats[0]`.

`formats[0]` — это **порядок перечисления драйвера**. Если поверхность не
предложит sRGB, движок отрендерит линейный цвет в UNORM-аттачмент, и картинка
будет выглядеть значительно темнее/бледнее — без единой ошибки. Правильный
fallback — `B8G8R8A8_UNORM` + ручная гамма-кодировка в шейдере, либо явный
`ERROR_SURFACE_LOST_KHR`.

Проверил, что основной путь корректен: `geometry.wgsl:71` возвращает линейное
значение, аттачмент `B8G8R8A8_SRGB` — железо кодирует. Если sRGB доступен, всё
правильно. Риск только в fallback.

### 4.6. 🟡 Stale-документация, которая actively вводит в заблуждение

`present.rs:15-21`, шапка модуля:

> Because the CPU blocks on the render fence before presenting, the present does
> not need a wait semaphore — which also sidesteps `ash 0.38`, whose
> `queue_present` does not accept one.

**Это неправда.** `vk::PresentInfoKHR` имеет `p_wait_semaphores`, и `queue_present`
их прекрасно принимает. Ниже в том же файле, на строке 374, расписана Баг№282 —
про то, что семафор как раз нужен. Модуль описывает отменённое поведение как
актуальное.

Дубль — `present.rs:368-370`, первый абзац doc-комментария к `present()`:
> No wait semaphore is passed…

прямо противоречит следующим за ним шести абзацам, которые описывают, что
семафор нужен и без него баг.

Кто-то, разбирающийся в Vulkan и читающий по диагонали, вынесет из этого файла
ровно неверное правило.

### 4.7. 🟡 Мелкое

- `Drop for Swapchain` вызывает `device_wait_idle()` (`present.rs:452`) — полный
  стоп GPU при каждом пересоздании цепочки, то есть на каждом кадре ресайза.
- `Swapchain::cleanup` (`present.rs:431`) уничтожает image views **до**
  `device_wait_idle()`. Порядок неверный; это error-путь, но всё равно.
- `pipeline_cache.rs:54-66`: `data()` вызывает `get_pipeline_cache_data` дважды и
  делает `copy_from_slice` — при росте кэша между вызовами будет паника. Мёртвый
  код, но переписывая под кольцо буферов вы это унаследуете.
- `create_semaphore` (`present.rs:466`) — мёртвая.
- `acquire` возвращает `SwapchainOutOfDate` на `SUBOPTIMAL` (`present.rs:335`),
  хотя `SUBOPTIMAL` по спецификации разрешает отрисовать ещё кадр. На перетаскивании
  окна это пересоздание цепочки на каждом кадре.
- `create_texture` жёстко требует `DEVICE_LOCAL` и игнорирует `desc.memory_flags`
  (`device.rs:799`). Создать текстуру в host-visible памяти нельзя. Для динамического
  текста UI и readback-целей это ограничение.

### 4.8. 🟢 Что сделано правильно

- **Validation layer подключён по-настоящему** (`instance.rs:142-198`): проверка
  наличия слоя, `debug_utils` messenger, `destroy_debug_utils_messenger` в Drop.
  Это редкость и именно благодаря ему авторы нашли причину №282.
- `API_VERSION = 1.3` (`instance.rs:19`), при этом `PhysicalDeviceVulkan12Features`
  подключён через `p_next` — правильно для 1.1+ (`device.rs:123-141`).
- `VK_KHR_maintenance4` в списке расширений — редкая, правильная забота.
- `DeviceQueueCreateInfo` всегда с `queue_count: 1` — корректно, семейства с
  несколькими очередями обрабатываются аккуратно.
- `submit_lock` покрывает всё окно «reset → begin → record → end → submit → wait»,
  а не только reset (`device.rs:558`). Закрытие Баг№177 сделано аккуратно.
- `mip_size`, `format_size` — единый источник правды, покрыт тестами
  (`depth_texel_sizes_are_correct`, `compressed_formats_report_a_block_size_not_zero`).

## 5. Рендер-слой

### 5.1. 🔴 Дефект в цепочке постпроцессинга (латентный)

`src/render/postprocess/manager.rs:63-97`:

```rust
let mut current = input;
let mut temp = output;
// hdr:     apply(input  -> output);  swap → current=output, temp=input
// bloom:   apply(output -> input);   swap → current=input,  temp=output
// dof:     apply(input  -> output);  swap → current=output, temp=input
// motion:  apply(output -> input);   swap → current=input,  temp=output
// fxaa:    apply(current, output)
```

Четыре свопа — чётное число, `current` возвращается к `input`. **FXAA читает
исходный вход и пишет в `output`, затирая результат всей цепочки.**

Сегодня не видно, потому что все пять эффектов — pass-through. Это мина: как
только кто-то реализует bloom, результат будет молча пропадать, и диагностировать
будет нечего. Одна поправка: либо убрать последний своп, либо применять FXAA к
`current` и в отдельный выход.

### 5.2. 🔴 `lighting.rs:398` — все текстуры в один слот

```rust
for (_name, resource) in resources {
    if let Some(view) = resource.view() {
        encoder.bind_texture(view, 0);   // ← всегда 0
    }
}
```

Каждая текстура графа биндится в слот 0. В итоге остаётся последняя, а порядок
обхода `HashMap` недетерминирован — то есть результат меняется от запуска к
запуску. Слот должен браться из имени ресурса или из схемы биндингов пасса.

Сейчас безвредно (в пассе нет draw), но это код, который сломается первым, когда
пасс начнут делать настоящим.

### 5.3. 🟡 Отсечение — мёртвое

`src/render/scene/scene.rs:26`:

```rust
/// Frustum culler
_frustum_culler: FrustumCuller,
```

Подчёркивание в имени — поле намеренно не используется, чтобы не было warning'а.
Сама `culling.rs` (извлечение плоскостей фрустума по Gribb-Hartmann) написана
корректно — и не вызывается ни разу. Для навального боя с сотнями юнитов
frustum culling это первая необходимая оптимизация.

Рядом в `mod.rs:26` висит `//! - Frustum/Occlusion Culling` в списке возможностей.

### 5.4. 🟡 `transparent.rs` — мёртвая работа

Объекты фильтруются, мапятся в `TransparentObject` с дистанцией и blend-режимом,
сортируются двумя режимами... и `transparent_objects` после сортировки не
используется ни для одного draw. Сортировка на пустом месте каждый кадр.

### 5.5. 🟡 `Renderer::initialize` добавляет ресурсы, но не пассы

`graph.rs:67-75` — сигнатура принимает `_device`, `_scene` с ведущими
подчёркиваниями. Пассы не создаются. См. §1.1.

### 5.6. 🟢 Что сделано правильно

- **`geometry.rs` — сильная работа.** Комментарии объясняют *почему* extent берётся
  из фреймбафера, а не из `context.resolution` (масштабирование Windows 125%:
  логическое 1280×720 → физическое 1600×900, замороженный вьюпорт рисует в углу).
  Это ровно тот класс бага, который обычно обнаруживают через месяц.
- `mesh.rs` — тест `plane_triangles_face_the_same_way_as_their_vertex_normals`;
  намотка исправлена по реестру.
- `base.rs` — `get_texture`/`get_buffer`/`get_texture_view` возвращают `Option`
  вместо `unwrap`. Правильная замена после Баг№186.
- Разбиение на пассы/граф/сцену/материалы — архитектурно разумное, это не спагетти.

## 6. Системная проблема

Смотрю на всё вместе, и картина не в отдельных дефектах.

**Паттерн: подсистема пишется целиком, полируется, покрывается тестами — и не
подключается.**

| Подсистема | Строк | Состояние |
|---|---:|---|
| D3D12 / D3D11 / OpenGL бэкенды | 1 696 | не компилируются, нет `mod` |
| `rhi/memory/` (buddy, pool, linear, heap) | 1 158 | никем не используется |
| `pipeline_cache.rs` | 76 | не подключён, вызовы = `null` |
| `prelude.rs`, `ui/theme.rs` | ~400 | не подключены |
| ray tracing / mesh shading / acceleration | ~1 200 | нет зависимостей, нет вызовов |
| Frustum culling | ~300 | поле `_frustum_culler` |
| Постпроцессинг (5 эффектов) | 1 069 | pass-through |

Итого около **6 000 строк** кода, который не выполняется ни в одном бинаре.

При этом качество **написанного** — высокое. `geometry.rs`, выбор memory type,
teardown по зависимостям, validation layer, объяснения в комментариях — это
уровень, которого большинство проектов не достигает вообще.

Проблема не в качестве, а в том, что **нет критерия «это работает»**. Ни один
из этих модулей не был заблокирован сборкой, тестом или рендером пикселя.
Сборка проходит, тесты проходят, «зелёный статус» в реестре — а рендера нет.

**Про `lib.rs` отдельно.** Заявленные «Ray Tracing, Mesh Shading, VRS, Bindless»
и четыре поддерживаемых API — это описание намерения, а не состояния. Единственный
читатель этого файла (человек вроде вас) сделает из него вывод, противоположный
факту. В проекте, где всё остальное документировано настолько честно (реестр
дефектов — образец), это единственное место, где документация actively врёт.

   отрисовать ничего из своих собственных ассетов.** Это самый высокий
   ROI- пункт из всех.

   реализацией эффектов.

**Потом (нужно для жизни движка):**

   buffer, fence и семафор на слот. Это закрывает и №282, и потолок
   производительности, и проблему лимита аллокаций заодно. По их же записи —
   это единственное правильное лечение.
6. **Подключить `rhi/memory/`** вместо `backend/vulkan/memory.rs`. 823 готовые

7. **Общий пул дескрипторов** вместо пула-на-сет.

   биндингов). Портрет готов — `Tool/client_tests/assets/shaders/gbuffer.spv`

9. Включить `_frustum_culler`.

**Регламент:**

10. В `BUGS.md` ввести колонку «проверено в этом коммите» с командой и её выводом.
    Сейчас «Исправлен» ставится по наличию блока «Исправлен как» — но блок
    пишется по памяти о работе, а не по факту сборки. Стоимость проверки — одна
