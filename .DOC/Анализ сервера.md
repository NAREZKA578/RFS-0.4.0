**Дата:** 2026-10-15
**Автор:** AGENT-SBF1
**Предмет:** `server_src/` целиком (~18 400 строк Rust в 7 крейтах) + `Tool/harness`
**Правок в код не вносилось.** Это отчёт, а не правка.

---

## 0. Метод и границы

**Что делалось.** Чтение всех файлов `server_src/crates/*` и `Tool/harness`, независимый
разбор по восьми осям, сквозная трассировка одного матча от `main()` до конца, и
адверсарная проверка двадцати утверждений — с попыткой их **опровергнуть**, а не
подтвердить. Плюс выборочная ручная верификация ключевых находок по исходникам.

**Восемь осей:** тик и детерминизм · сетевой слой · граница доверия и урон ·
производительность · жизненный цикл и эксплуатация · архитектура и владелец
истины · сквозная трассировка матча · адверсарная проверка.

**Проверено лично (я смотрел в исходники сам):** помечено `[✓]` ниже.
`[п]` — подтверждено вторым аналитиком независимо. Остальное — `[?]` означает
«прочитано, но не проверено запуском».

**Чего я не делал:** не запускал сервер под нагрузкой, не профилировал, не
измерял бенчмарки (их в репозитории нет вообще — см. §7), не открывал сокет.

**Важное замечание о числах.** Часть находок сначала была оценена в драматических
величинах, и адверсарная проверка их снизила. Ниже приведены **исправленные**
числа. Например, амплификация во фрагментации — не 831 МБ, а ~1,7 МБ на соединение;
терминальная скорость фрегата — не 1414 м/с, а ~2739 м/с. Ни одна из этих цифр
не является поводом закрывать находку, но и поводом для паники — тоже.

## 1. Главное, одним абзацем

Сервер **собран, оттестирован (145 тестов) и выглядит работающим**, но он не
выполняет свою основную функцию: **попадание не наносит урон**. Это не
экзотический сценарий, а следствие арифметики трёх констант, которые ни разу не
были сверены друг с другом. Ниже этого уровня — ещё три класса дефектов:
граница доверия (сервер доверяет адресу отправителя), мёртвые подсистемы
(≈2 600 строк, включая **всю** подсистему распространения повреждений) и
тихая потеря данных при >64 сущностях в одной ячейке пространственной сетки.

Отдельно: единственный файл карты в репозитории **не грузится**, то есть
единственный документированный способ задать мир не работает. Это поломка от
удаления `ObstacleKind::Asteroid` 14.10, и её никто не заметил, потому что файл
не открывает ни один тест.

## 2. Уровень 1 — блокеры

### 2.1 Попадание не наносит урон. Геометрия не сходится

**Серьёзность: критично. Проверено лично.**

Снаряд летит 400 м/с, тик 1/30 с ⇒ **13,3 м за тик** `[✓ station.rs:272, time.rs:7]`.
Снаряд уничтожается в **том же тике**, в котором впервые пересёк AABB корабля
`[✓ tick.rs:417 → 424 → 592-597]`, и в `CollisionEvent` записывается **конец**
отрезка, а не точка входа:

```rust
// sim/src/tick.rs:417-427
if segment_intersects_bounds(proj.prev_position, proj.position, &bounds) {
    let normal = Self::calculate_impact_normal(ship, proj.position);
    collisions.push(CollisionEvent {
        ...
        position: proj.position,      // <- конец отрезка, не точка попадания
```

По этому `position` считается урон `[✓ tick.rs:608-652 → ship.rs:554]`.

Три числа, которые нигде не сверялись:

| что | значение | где |
|---|---|---|
| AABB корпуса (куда попадает снаряд) | ±50, ±30, **±150** | `[✓ ship.rs:754]` |
| Ближайший повреждаемый бокс (отсек) | x ±12, y −5…+6, z −70…+50 | `[✓ loader.rs:93-250]` |
| Ближайший повреждаемый бокс (пост) | ±2 вокруг точки внутри ±3 | `[✓ station.rs:390, loader.rs:253-497]` |
| Радиус, дальше которого урон = 0 | **12,0** | `[✓ damage.rs:23]` |

**Минимальный зазор между поверхностью AABB и любым повреждаемым боксом — 24 м**
(верхняя палуба: корпус до y=30, отсек `crew_quarters` до y=6). По остальным осям:
38 (борт), 80 (корма), 100 (нос).

Кривая затухания: `falloff(d) = 0.0` при `d >= max_damage_radius = 12` `[✓ damage.rs:270-273]`.
Следовательно:

```rust
// damage.rs:116 и 210
let damage_dealt = damage * factor * direct_damage_multiplier;   // = damage * 0.0 = 0
if damage_dealt <= 0.0 { continue; }

// damage.rs:220-226 — урон корпусу масштабируется ЛУЧШИМ фактором по отсекам
let hull_factor = max_factor;                                    // = 0.0
target.apply_health_damage(damage * hull_damage_multiplier * hull_factor);   // = 0
```

**Корпус получает нулевой урон. Отсеки и посты — нулевой.** Попадание
регистрируется (`ShipHit` уходит клиенту, `HitMark` кладётся в слой 0), но
**ни одна единица состояния не меняется никогда**.

**Единственное исключение — узкий угол.** Если выстрел входит в палубу над
`crew_quarters` и его конец отрезка оказывается на 13,3 м **внутри** корпуса,
расстояние до отсека падает до ~10,7 м, `falloff ≈ 0,055`, и ядро наносит ≈5 урона
из 10 000. То есть даже в этом углу корабль получает 0,05 % залпа.

**Почему это не поймали тесты.** `Tool/harness/tests/damage.rs` вызывает
`apply_damage_to_ship` напрямую, с точкой внутри корпуса. Ни один тест не
проводит полный путь «снаряд → AABB → позиция попадания → урон» и не сверяет,
что расстояние от позиции до повреждаемого бокса вообще попадает в
`max_damage_radius`.

**Что чинить (три варианта, выбор не мой):**
- (А) Прописать в `tick.rs` реальную точку входа в AABB вместо `proj.position`
  (тот же slab-расчёт, что в `map.rs::swept_obstacle`, но уже выбрасывается);
- (Б) Увеличить `max_damage_radius` до величины ≥ расстояния корпус→отсек (то есть
  до ~100), а кривую перенастроить;
- (В) Считать урон по расстоянию до **корпуса**, а не до каждого отсека, и
  определять пострадавший отсек отдельно (как при пробитии переборки).

Любой из трёх требует теста, который **краснеет**: «выстрел в борт наносит
корпусу ожидаемый урон».

### 2.2 Единственный файл карты не грузится

**Серьёзность: критично. Проверено лично + подтверждено запуском.**

```
assets/maps/open-water-50km.json:14,22,30   "kind": "Asteroid"
sim/src/map.rs:70-74                        ObstacleKind { Structure }   // Asteroid удалён 14.10
```

`[✓ оба факта подтверждены мной; [п] запуск воспроизвёл отказ:
unknown variant 'Asteroid', expected 'Structure' at line 14 column 24]`

Это **регрессия**: `.DOC/AGENT_CHAT.md:2412` показывает, что 14.10 тот же самый
запуск проходил (`obstacles=4`) — то есть файл чинили в тот же день, когда
удаляли `Asteroid`, и не перечитали файл.

Ни один тест в репозитории не открывает `assets/maps/*`. Единственный файл карты,
единственный документированный способ задать мир, и **ноль** тестового покрытия.

### 2.3 Собственный код учит, что дефект ловится негативным контролем — и не учит этому тест карты

Отдельная, но связанная мысль. Репозиторий уже содержит `tests/module_tree_reachability.rs`
и `pass_reachability.rs` — инструменты против класса «написано и не подключено»,
и они работают. Но нет инструмента против класса **«подключено, и падает при первом же
использовании»**. Механизм, который бы поймал 2.2, тривиален: один тест, который
перебирает `assets/maps/*.json` и проверяет, что каждый грузится. Стоит тридцать
строк. Это предложение, не директива.

### 3.5 Архитектура: владелец истины

Границы крейтов **выдержаны**: граф зависимостей строго DAG, ни одного цикла,
`damage` не знает о `ship` (решено инверсией через трейт `DamageTarget` — единственное
правильное архитектурное решение в проекте, его надо сохранять).

Проблема не в границах, а в **дублировании данных**:

> Отсек описан **7 раз**, корабль — **6**, пост — **6**, снаряд — **5**.
> Три разные структуры в трёх крейтах называются `CompartmentState`.

**Ключевое расхождение, уже случившееся:**

```
ShipState.compartment_states[id]          <- ИСТИНА затопления (compartment.rs:44)
   ├─► Compartment::compute_water_spread   <- единственный реальный поток воды
   └─► DamageGraph / CompartmentNode        <- ВТОРАЯ модель (graph.rs:9)
         пишется из живого пути (damage.rs:190 при каждом попадании)
         читается ОДНО поле: is_breached
         current_level / fire_intensity / is_sealed — пишутся и не читаются никем
```

Отдельно: рёбра графа создаются в `register_topology` (единственный вызов —
конструктор корабля) и **навсегда остаются `is_sealed: true`**. `Ship::set_bulkhead_seal`
пишет только в `ShipState`. Синхронизации A→B нет. То есть если кто-то когда-нибудь
подключит `PropagationSystem`, вода по переборке пойдёт в одной модели и не пойдёт
в другой, и **обе будут правы**.

## 4. Сквозная трассировка: что получится, если запустить матч

Отдельный угол. Не «ищем баги», а «смотрим, что увидит человек».

### 4.1 Корабль №16 не может ничего делать

На фрегате **15 постов** `[✓ loader.rs — ровно 15 StationTemplate]`, один игрок =
один пост `[✓ ship.rs:601-609]`. Игрок №16 подключается, получает снапшот, видит
корабль, и может:
- **не** занять пост (`ack(false, "cannot occupy station")`);
- **не** стрелять (`commands_station` требует оккупации);
- **не** рулить (штурвал занят);
- **но может** `SealBulkhead` / `ActivatePump` / `RepairStation` / `ExtinguishFire` —
  эти шесть команд проверку оккупации **не проходят** (3.1.2).

То есть дефект границы доверия и дефект конфигурации сходятся в одной точке:
игрок, которому нельзя играть, может ремонтировать и герметизировать.

Лимит `crew_max: 40` объявлен `[✓ loader.rs:499]` и **не проверяется нигде**.

### 4.2 Выйти из поста вводом нельзя

`InputActions::STATION_EXIT` **не читается сервером** — `apply_input` смотрит
только на `move_forward`, `move_right`, `yaw` и `station_interaction` `[п]`.
Выход возможен исключительно через `ServerCommand::ExitStation`. Клиент, который
«нажал E», останется сидеть.

### 4.3 Дроссель защёлкивается, топливо не тратится

Нет ни таймаута до нейтрали, ни «рулевой погиб», ни авто-сброса. Последнее
значение живёт вечно. `fuel` не меняется нигде — корабль может идти полным ходом
бесконечно.

### 4.4 Что состояние реплицируется, а что нет

| состояние | есть в коде | реплицируется | клиент видит |
|---|---|---|---|
| Положение/курс/скорость корабля | да | слой 0 | **да** |
| Прочность корпуса | да | слой 0 | да, и **всегда 10000** (см. 2.1) |
| Топливо | да | слой 0 | да, и **никогда не тратится** |
| `is_sinking` / `has_sunk` | да | **нет** | **нет** |
| Отсек: вода / герметичность / пробит / помпа | да | слой 0 вложенно | да, но **всегда исходное значение** |
| Отсек: **имя** | да | **нет** | **нет** |
| Отсек: **габариты** | да | **нет** (конверсия в снапшот выбрасывает) | только точка центра |
| Отсек: **состояние переборок** | да | **нет** | **нет** |
| Пост: тип, позиция, оккупант, патроны, HP | да | слой 1 | **да** |
| Пост: **wp** | да | **нет** (выброшено) | **нет** |
| Снаряд: позиция, скорость, урон, пробитие | да | слой 3 | **да** |
| Снаряд: радиус взрыва, время жизни, `has_exploded` | да | **нет** (выброшены) | **нет** |
| Игрок: позиция / HP / стамина | да | слой 2 | да, но позиция **одинаковая у всех** `(0, 4, -8)`, HP/стамина — константы 100 |
| Игрок: **имя** | литерал `"player"` | слой 2 | да, **одинаковое у всех** |
| Огонь (`fire_intensity`) | да | слой 0 | да, и **всегда 0.0** — источника возгорания не существует |
| Счёт / команды / фазы матча / победитель | **нет** | — | — |
| Сохранение матча на диск | **нет** | — | — |

### 4.5 Пожар недостижим

`Compartment::set_fire`, `DamageGraph::set_fire`, `PropagationSystem::ignite_fire`
вызываются **только из тестов** `[п]`. Единственные записи `fire_intensity` в живом
сервере — распространение от **уже** горящего соседа и обнуление. При этом
`ServerCommand::ExtinguishFire` возвращает `true` и acked-успех, то есть команда
«пожар потушен» уходит в пустоту. `GameEvent::FireStarted` / `FireExtinguished`
не порождаются.

### 4.6 Конец матча не наступает ни в каком смысле

`match_id` — случайный `Uuid`; ни состояния матча, ни счёта, ни фаз, ни таймера.
`Respawn` → `"command not implemented"`. Закончить матч нечем — и узнать, что он
закончился, тоже нечем.

## 7. Предлагаемый порядок работ

Не приоритет «важнее», а порядок, в котором каждый шаг **даёт наблюдаемый
результат** и не ломает следующий.

**Шаг 1. Урон (2.1).** Пока это не сделано, всё остальное обсуждать бессмысленно:
матч идёт, попадания регистрируются, состояние не меняется. Начинать с теста,
который краснеет: «выстрел в борт с 300 м наносит корпусу ожидаемый урон».
Три варианта решения — в §2.1; выбор не мой.

**Шаг 2. Карта (2.2).** Три строки в JSON. Плюс тест, перебирающий
`assets/maps/*.json` — иначе это повторится на следующей правке перечисления.

**Шаг 3. Конфигурация по умолчанию (3.7.3, 4.1).** `--ships` по умолчанию 1
означает, что заявленный сценарий (200 игроков, 15–40 кораблей) не воспроизводим
иначе как флагом, который попутно ломает размер мира. Либо дефолт ≥15, либо
явный отказ, либо документированная связь «корабли ⇒ размер мира».

**Шаг 4. Граница доверия (3.1.2–3.1.5).** Порядок именно такой: сначала
`commands_station` на шесть команд (одна функция), затем `is_finite` в `Repair`
(одна строка), затем тип поста (один предикат). Токен в `ConnectAccept` (ядро
№216) — большое изменение протокола, его отдельно.

**Шаг 5. Потеря данных в репликации (3.2.1–3.2.3).** `all_entities` + `spilled`,
конверсия `CompartmentEntity`, `remove_entity_from_interest`. Все три — тихая
порча, и все три в одном слое.

**Шаг 6. Наблюдаемость (3.6.1–3.6.4).** Счётчик отказов, счётчик отброшенных
снарядов, счётчик пропущенных тиков, `ships=` как факт, Ctrl-C handler. Пока
этого нет, всё вышеперечисленное приходится ловить вручную.

**Шаг 7. Производительность (3.4.1–3.4.2).** Клоны карты и `ShipState` — самые
дешёвые из всех находок: три строки, три строки.

**Дальше — по факту замеров.** Без бенчмарка разговор о 3.4.3 и 3.4.4 остаётся
оценкой. Первыми стоит сделать `criterion`-бенчмарки на `TickSystem::tick` при
1/16/64 кораблях и на `build_snapshot` при 1/50/256 клиентах.

   фикса — прогон с отключённой правкой. Для 2.1 это обязательно: тест должен

2. **«Зелёная сборка» не означает «работает».** 2.1, 2.2, 3.2.1 — все три были
   зелёные. Класс «подключено, но не работает» ловится только прогоночным
   сценарием, не юнит-тестом.
3. **Бинарный критерий обязан иметь ненулевой фон.** Прямо из чата, п. «Offscreen дожат».
4. **Тест на константу — тоже тест.** Для 3.5 (арифметика `SHIP_ID_STRIDE`)
   уместнее `assert!(3000 + MAX_COMPARTMENTS * 8 <= SHIP_ID_STRIDE)`, чем
   моделирование 900 отсеков.
5. **Проверять достижимость до приоритета.** Адверсарная проверка снизила
   три находки с «критично» до «слабо»: амплификацию фрагментации (300 МБ, а не
   831), двойное попадание (нужна скорость 87 км/с), дедлок дельты (>512
   сущностей в слое). Они остаются дефектами, но чинить их раньше 2.1 — ошибка
   приоритета.
6. **Значения из конфига — сверять с константами, с которыми они работают.**
   Ни одна из трёх констант в §2.1 не была написана рядом с другой. Держать их
