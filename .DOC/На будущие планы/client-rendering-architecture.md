# Архитектура рендера

Клиентская часть, отдельно от сети/сервера (тот план — в network-server-architecture.md). Часть решений ниже — прямые следствия того, что уже решено в основном плане: реализм как направление, полный хендролл Vulkan/DX12/DX11 вместо готовой прослойки, "без сокращений" как явно заявленная цель.

Три вопроса в конце документа — единственное, что реально требует твоего решения, а не инженерного рассуждения. Всё остальное — рабочий план, который можно поправить, если что-то не так.

---

## 1. Общее направление

- **Художественное направление** — реализм, но не как требование симулировать каждую мелочь до предела: реализм как направление и ощущение (материалы, освещение, пропорции ведут себя правдоподобно), не как самоцель дотошной симуляции каждой детали. Согласуется с уже принятыми решениями по всему проекту — упрощённая формула Торричелли вместо полной гидродинамики, отказ от полноценной симуляции подлодки (раздел 17.3), отказ от отдельной механики подпорок переборок (раздел 13). Подтверждено.
- **Цель по fps** — 200 fps на базовом уровне железа (3090 Ti) остаётся целью, но не приоритетом прямо сейчас: сначала весь функционал делается полностью и до рабочего состояния, оптимизация — отдельная, осознанная фаза после этого, не одновременно с разработкой. Важная оговорка: это про порядок работ, не про архитектуру — решения вроде двухфазного тика, ECS на архетипах, Forward+ остаются как есть именно потому, что переделывать фундаментальную архитектуру постфактум ради производительности намного дороже, чем заложить её верно с самого начала.
- **Целевое разрешение** — 1440p как база для расчёта производительности: заметно лучше 1080p по чёткости, заметно дешевле 4K по нагрузке. Сам рендер поддерживает разные разрешения, это не жёсткое ограничение архитектуры, просто ориентир для бюджета.
- **Трассировка лучей** — не основа конвейера, а опциональная надстройка поверх растеризации (отражения/тени по трассировке лучей как переключаемая опция для мощного железа). Полный путь трассировки лучей в реальном времени и стабильные 200 fps на базовом железе — комбинация, которая пока не сходится даже у AAA-студий; растеризация с точечными RT-улучшениями сверху даёт контроль над этим компромиссом, а не жёсткий выбор один раз и навсегда.
- **Апскейлинг (DLSS/FSR/XeSS)** — часть плана, стандартная практика для попадания в целевой fps без потери чёткости картинки.

## 2. Три графических API

### 2.1 Порядок реализации

Vulkan первым: кроссплатформенный, на нём проверяется сама архитектура RHI (раздел 2.3), прежде чем размножать её ещё на два бэкенда. DX12 вторым — концептуально близок к Vulkan (явное управление памятью, похожая модель команд и синхронизации), меньше нового поверх уже проверенного на Vulkan. DX11 последним — другая парадигма (менее явное управление, драйвер берёт на себя больше), самостоятельная работа, не расширение первых двух.

### 2.2 Шейдеры — открытый вопрос, не решено

Предлагался единственный исходник на HLSL, компилируемый официальным компилятором Microsoft (DXC) и в DXIL (DX12), и в SPIR-V (Vulkan). Под вопросом — пользователь думает над этим отдельно, не финально.

Замечено 22 октября: в этом предложении не было DX11, хотя он третий бэкенд (раздел 2.1). По документации Microsoft, DXC — это шейдерная модель 6, а модели 2–5.1, которые понимает DX11, собирает старый компилятор FXC (новее 5.1 FXC не пойдёт: «fxc will not support shader models beyond the current v5.1»). Для Vulkan DXC делает SPIR-V и принимает в том числе модели 5.1 и ниже — кроме возможностей, у которых нет аналога в Vulkan (руководство Vulkan). Из этого следует: один исходник на все три API возможен, если общие шейдеры написаны в подмножестве модели 5.1 — для DX11 их собирает FXC, для Vulkan и DX12 — DXC; всё новее 5.1 (трассировка лучей, mesh-шейдеры, операции волн) — только отдельными вариантами под Vulkan и DX12. Сопоставление привязок ресурсов между API (`register` у HLSL и `[[vk::binding]]` у Vulkan) руководство Vulkan описывает как решаемое небольшими вставками. Не проверено, оценка моя: хватит ли модели 5.1 на всё запланированное (Forward+, каскадные тени, океан, SSR, TAA) — проверяется на первых шейдерах. Если от DX11 откажутся, ограничение снимается. Два других пути (отдельные шейдеры под каждый API; свой компилятор шейдеров) — примерно втрое больше работы (моя оценка) и отдельный большой проект соответственно; не рекомендуются.

### 2.3 RHI — контракт поверх всех трёх

Единственное место в движке, которое знает о конкретном графическом API — тот же паттерн, что был замечен в исходном коде в самом начале всего проекта (там он существовал только как заготовка с мёртвыми, никогда не реализованными ветками под DX11/DX12). Сделанный по-настоящему, сейчас, — закрывает тот старый пробел взаправду.

### 2.4 Окно и ввод — готовая библиотека, не своя

`winit` (или аналог) — рутина без творческой ценности: сотни специфичных для конкретной ОС мелочей ради нуля отдачи для геймплея. Ровно тот класс зависимостей, который сам проект с самого начала разговора выносил за скобки принципа "всё своими руками" — код, а не игровая логика.

### 2.5 Платформы

Только Windows — Linux не в планах. DX11/DX12 в любом случае Windows-специфичны, а раз Linux не нужен, дисциплина по изоляции платформенного кода от ядра игры не требуется как отдельная забота.


## 3. Конвейер рендера

**Forward+ (кластерный forward)** — не classic forward и не чистый deferred. В игре много прозрачности разом (вода, дым, дипольные помехи, туман, брызги) — классическая слабость чистого deferred, где прозрачные объекты требуют отдельного, неудобного прохода поверх основного конвейера. Forward+ справляется с прозрачностью так же естественно, как обычный forward, но при этом эффективно тянет много источников света одновременно за счёт группировки их по экранным кластерам — не нужно перебирать все источники света для каждого пикселя.

Подтверждено как план: Forward+ — не чужая библиотека и не готовый код, а общая стратегия организации рендера, реализуемая полностью своими руками, как и всё остальное в проекте.

## 4. Освещение и тени

- **Тени** — каскадные тени для направленного (солнечного) света.
- **Глобальное освещение** — световые пробники (заранее просчитанные или обновляемые) плюс экранно-пространственные отражения как основа. Полный динамический GI (уровня Lumen) — исследовательская задача, на которую у выделенной команды уходят годы; повторять её не пытаемся, тот же вывод, что уже был сделан при выборе общей стратегии движка.
- **Трассировка лучей** — опциональная надстройка (отражения/тени) поверх этой основы для мощного железа, не замена ей.

## 5. Сглаживание и постобработка

- **TAA** — согласуется с апскейлингом (DLSS/FSR/XeSS используют тот же принцип временного накопления кадров внутри себя, это не два разных решения).
- **Обязательная постобработка**: тонмаппинг, bloom, цветокоррекция.
- **Размытие в движении** — выключено, подтверждено: мешает читаемости боя.
- **Глубина резкости** — не вижу геймплейной причины держать включённой во время самого боя; годится для менюшных/кат-сцен-подобных моментов, если такие будут.
- **HDR-вывод на экран** — да: внутренний расчёт освещения и так идёт в HDR, вывод в HDR на экран — небольшая добавка поверх уже готового, не новая архитектура.

## 6. Мир и эффекты — преемственность с основным планом

- **Океан** — волновой спектр (сумма нескольких волн разной длины) + порог по крутизне для пены + GPU-частицы брызг, всё завязано на одну переменную "сила непогоды" — план не меняется (раздел 12.3 основного документа).
- **Volumetrics** (туман, дым, лучи света) — тесно связаны с погодой и дымовыми завесами/дипольными отражателями (разделы 11, 15.4 основного документа): объёмный туман от силы непогоды, объёмный дым от дымовых завес и пожаров, лучи света — низкий приоритет, красиво, но не критично.
- **Частицы** — GPU-driven, начальный набор по тому, что уже требует геймплей: брызги волн, дым, огонь, взрывы (в том числе взрыв погреба, раздел 10.3 основного документа).
- **LOD** — классические цепочки LOD по расстоянию, не попытка повторить виртуализированную геометрию уровня Nanite — тот же вывод, что и по GI, тот же вывод, что был сделан при выборе стратегии движка в целом.

## 7. Инструменты разработки

- **Отладочные метки для RenderDoc/PIX** — закладываются в вызовы API с первого дня: дёшево сделать сразу, дорого добавить постфактум, когда уже накопился код без них.
- **Горячая перезагрузка шейдеров** — для скорости итерации при разработке, отдельно от механизма кросс-компиляции из раздела 2.2.

## 8. Отдельно, не сейчас

UI/HUD (интерфейс, тактическая карта из раздела 15.6 основного документа, меню) — прямо связан с рендером, но достаточно самостоятельная тема, чтобы не решать её походя здесь. Отдельный разговор. В него войдут и экраны, которые уже вытекли из серверной части основного документа: меню «Серверы» (список через Steam, раздел 6.3), экран выбора фракции и страны при входе и смене стороны (раздел 20.7) и окно панели управления сервером (раздел 6.4) — его решено делать на собственном UI движка, поэтому оно ждёт, пока появится UI.
