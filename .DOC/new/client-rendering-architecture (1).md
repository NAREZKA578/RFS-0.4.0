# Архитектура рендера

Клиентская часть, отдельно от сети/сервера (тот план — в network-server-architecture.md). Часть решений ниже — прямые следствия того, что уже решено в основном плане: реализм как направление, полный хендролл Vulkan/DX12/DX11 вместо готовой прослойки, "без сокращений" как явно заявленная цель.

Что ещё остаётся открытым — в конце документа. Всё остальное — рабочий план, который можно поправить, если что-то не так.

---

## 1. Общее направление

- **Художественное направление** — реализм, но не как требование симулировать каждую мелочь до предела: реализм как направление и ощущение (материалы, освещение, пропорции ведут себя правдоподобно), не как самоцель дотошной симуляции каждой детали. Согласуется с уже принятыми решениями по всему проекту — упрощённая формула Торричелли вместо полной гидродинамики, отказ от полноценной симуляции подлодки (раздел 17.3), отказ от отдельной механики подпорок переборок (раздел 13). Подтверждено.
- **Цель по fps** — 200 fps на базовом уровне железа (3090 Ti) остаётся целью, но не приоритетом прямо сейчас: сначала весь функционал делается полностью и до рабочего состояния, оптимизация — отдельная, осознанная фаза после этого, не одновременно с разработкой. Важная оговорка: это про порядок работ, не про архитектуру — решения вроде двухфазного тика, ECS на архетипах, Forward+ остаются как есть именно потому, что переделывать фундаментальную архитектуру постфактум ради производительности намного дороже, чем заложить её верно с самого начала.
- **Целевое разрешение** — 1440p как база для расчёта производительности: заметно лучше 1080p по чёткости, заметно дешевле 4K по нагрузке. Сам рендер поддерживает разные разрешения, это не жёсткое ограничение архитектуры, просто ориентир для бюджета.
- **Трассировка лучей** — не основа конвейера, а опциональная надстройка поверх растеризации (отражения/тени по трассировке лучей как переключаемая опция для мощного железа). Полный путь трассировки лучей в реальном времени и стабильные 200 fps на базовом железе — комбинация, которая пока не сходится даже у AAA-студий; растеризация с точечными RT-улучшениями сверху даёт контроль над этим компромиссом, а не жёсткий выбор один раз и навсегда.
- **Апскейлинг (DLSS/FSR/XeSS)** — часть плана, стандартная практика для попадания в целевой fps без потери чёткости картинки.

## 2. Три графических API

### 2.1 Порядок реализации

Vulkan первым: кроссплатформенный, на нём проверяется сама архитектура RHI (раздел 2.3), прежде чем размножать её ещё на два бэкенда. DX12 вторым — концептуально близок к Vulkan (явное управление памятью, похожая модель команд и синхронизации), меньше нового поверх уже проверенного на Vulkan. DX11 последним — другая парадигма (менее явное управление, драйвер берёт на себя больше), самостоятельная работа, не расширение первых двух.

### 2.2 Шейдеры — один исходник на HLSL (решено 22 октября)

Решено 22 октября: один исходник на HLSL для всех трёх API. Слова пользователя (опечатки исправлены): «Насчёт шейдеров я бы предложил каждый свой, для гибкости настройки шейдеры для его оптимизации. Но раз в трое меньше работы есть, выбираем HLSL, звучит хорошо, только я не совсем понимаю как...». Прежняя пометка «открытый вопрос» снята.

**Как это работает, простыми словами**

- Шейдер — маленькая программа для видеокарты: считает цвет пикселя, положение вершины и тому подобное. У каждого графического API свой формат, который понимает его драйвер: Vulkan читает SPIR-V, DX12 — DXIL, DX11 — DXBC. Писать шейдеры «по-родному» под каждый API — значит держать три набора одних и тех же программ; отсюда «втрое больше работы».
- Вместо этого каждый шейдер пишется один раз на HLSL — это текстовый язык, похожий на C. Это исходник: его читают и правят люди.
- При сборке игры готовые программы-переводчики от Microsoft превращают этот один исходник в три готовых файла: DXC → SPIR-V для Vulkan, DXC → DXIL для DX12, FXC → DXBC для DX11. Игра при запуске загружает тот файл, который нужен выбранному API. Переводить прямо во время игры не нужно (моё предложение: переводить заранее, при сборке).
- Что остаётся «по-API» руками. Во-первых, небольшие вставки внутри того же файла вида `#if VULKAN … #elif DX12 …` там, где одному API нужна своя настройка — именно так сохраняется «гибкость под оптимизацию», о которой писал пользователь. Во-вторых, привязка ресурсов: `register` (HLSL) и `[[vk::binding]]` (Vulkan) пишутся рядом в одном исходнике. В-третьих, отдельные шейдеры только под Vulkan и DX12 для того, чего нет в DX11 (трассировка лучей, mesh-шейдеры и т. п.). Единый исходник не запрещает исключений: если какому-то одному шейдеру понадобится отдельная версия под API, её можно сделать отдельным файлом.
- Во время разработки: меняешь исходник — программа-переводчик пересобирает шейдер на лету, движок подхватывает (горячая перезагрузка, раздел 7; моё предложение).

Условие, которое из этого следует. Замечено 22 октября: в первом предложении не было DX11, хотя он третий бэкенд (раздел 2.1). По документации Microsoft, DXC — это шейдерная модель 6, а модели 2–5.1, которые понимает DX11, собирает старый компилятор FXC (новее 5.1 FXC не пойдёт: «fxc will not support shader models beyond the current v5.1»). Для Vulkan DXC делает SPIR-V и принимает в том числе модели 5.1 и ниже — кроме возможностей, у которых нет аналога в Vulkan (руководство Vulkan). Из этого следует: один исходник на все три API возможен, если общие шейдеры написаны в подмножестве модели 5.1 — для DX11 их собирает FXC, для Vulkan и DX12 — DXC; всё новее 5.1 (трассировка лучей, mesh-шейдеры, операции волн) — только отдельными вариантами под Vulkan и DX12. Сопоставление привязок ресурсов между API (`register` у HLSL и `[[vk::binding]]` у Vulkan) руководство Vulkan описывает как решаемое небольшими вставками. Не проверено, оценка моя: хватит ли модели 5.1 на всё запланированное (Forward+, каскадные тени, океан, SSR, TAA) — проверяется на первых шейдерах. Если от DX11 откажутся, ограничение снимается. Отвергнуто: отдельные шейдеры под каждый API (примерно втрое больше работы — моя оценка; пользователь выбрал один исходник) и свой компилятор шейдеров (отдельный большой проект).

Замечание о зависимостях (раньше не обсуждалось): DXC и FXC — внешние инструменты Microsoft. Они работают при сборке (и в сборке разработчика — для горячей перезагрузки), а в готовую игру не входят, если шейдеры собраны заранее (моё предложение). Считаю, что это укладывается в правило «минимум сторонних зависимостей» так же, как winit, — поправь, если не так.

Найдено 28 октября: агенты рендера этого решения не видели и предлагают другое — оставить WGSL единственным исходником (подробности и вопрос к пользователю — в конце документа, «Что ещё открыто»).

### 2.3 RHI — контракт поверх всех трёх

Единственное место в движке, которое знает о конкретном графическом API — тот же паттерн, что был замечен в исходном коде в самом начале всего проекта (там он существовал только как заготовка с мёртвыми, никогда не реализованными ветками под DX11/DX12). Сделанный по-настоящему, сейчас, — закрывает тот старый пробел взаправду.

### 2.4 Окно и ввод — готовая библиотека, не своя

`winit` (или аналог) — рутина без творческой ценности: сотни специфичных для конкретной ОС мелочей ради нуля отдачи для геймплея. Ровно тот класс зависимостей, который сам проект с самого начала разговора выносил за скобки принципа "всё своими руками" — код, а не игровая логика.

### 2.5 Платформы

Только Windows — Linux не в планах. DX11/DX12 в любом случае Windows-специфичны, а раз Linux не нужен, дисциплина по изоляции платформенного кода от ядра игры не требуется как отдельная забота.


## 3. Конвейер рендера

**Forward+ (кластерный forward)** — не classic forward и не чистый deferred. В игре много прозрачности разом (вода, дым, дипольные помехи, туман, брызги) — классическая слабость чистого deferred, где прозрачные объекты требуют отдельного, неудобного прохода поверх основного конвейера. Forward+ справляется с прозрачностью так же естественно, как обычный forward, но при этом эффективно тянет много источников света одновременно за счёт группировки их по экранным кластерам — не нужно перебирать все источники света для каждого пикселя.

Подтверждено как план: Forward+ — не чужая библиотека и не готовый код, а общая стратегия организации рендера, реализуемая полностью своими руками, как и всё остальное в проекте.

## 4. Освещение и тени

- **Тени** — каскадные тени для направленного (солнечного) света.
- **Глобальное освещение** — световые пробники (заранее просчитанные или обновляемые) плюс экранно-пространственные отражения как основа. Полный динамический GI (уровня Lumen) — исследовательская задача, на которую у выделенной команды уходят годы; повторять её не пытаемся, тот же вывод, что уже был сделан при выборе общей стратегии движка.
- **Трассировка лучей** — опциональная надстройка (отражения/тени) поверх этой основы для мощного железа, не замена ей.

## 5. Сглаживание и постобработка

- **TAA** — согласуется с апскейлингом (DLSS/FSR/XeSS используют тот же принцип временного накопления кадров внутри себя, это не два разных решения).
- **Обязательная постобработка**: тонмаппинг, bloom, цветокоррекция.
- **Размытие в движении** — выключено, подтверждено: мешает читаемости боя.
- **Глубина резкости** — не вижу геймплейной причины держать включённой во время самого боя; годится для менюшных/кат-сцен-подобных моментов, если такие будут.
- **HDR-вывод на экран** — да: внутренний расчёт освещения и так идёт в HDR, вывод в HDR на экран — небольшая добавка поверх уже готового, не новая архитектура.

## 6. Мир и эффекты — преемственность с основным планом

- **Океан** — волновой спектр (сумма нескольких волн разной длины) + порог по крутизне для пены + GPU-частицы брызг, всё завязано на одну переменную "сила непогоды" — план не меняется (раздел 12.3 основного документа).
- **Volumetrics** (туман, дым, лучи света) — тесно связаны с погодой и дымовыми завесами/дипольными отражателями (разделы 11, 15.4 основного документа): объёмный туман от силы непогоды, объёмный дым от дымовых завес и пожаров, лучи света — низкий приоритет, красиво, но не критично.
- **Частицы** — GPU-driven, начальный набор по тому, что уже требует геймплей: брызги волн, дым, огонь, взрывы (в том числе взрыв погреба, раздел 10.3 основного документа).
- **LOD** — классические цепочки LOD по расстоянию, не попытка повторить виртуализированную геометрию уровня Nanite — тот же вывод, что и по GI, тот же вывод, что был сделан при выборе стратегии движка в целом.

## Что ещё открыто

Шейдеры решены (раздел 2.2), но агенты рендера этого решения не видели, и их позиция расходится с ним — это вопрос к пользователю. Что я вижу в репозитории (коммит `20dbf8c`, проверено 28 октября):

1. В папке `.DOC/На будущие планы/` лежит старая копия этого документа, где HLSL «под вопросом»; в списке решений агентов (`TODO.md`, блок A1) вопрос значится «не решено».
2. У них уже написаны 14 пар шейдеров на WGSL (13 программ — вершинный и пиксельный шейдеры — и один вычислительный, `cluster`); компиляция идёт через naga в `Tool/client_tests`, готовые `.spv` лежат рядом. По записи агентов, это уже решение владельца: naga не входит в сам движок (`rhi`) — SPIR-V получают в тестах и кладут в репозиторий готовым.
3. 27 октября агент AGENT-FIX рекомендовал владельцу оставить WGSL единственным исходником, а DXIL для DX11/DX12 получать автоматически (naga → HLSL → DXC): 26 из 27 точек входа собираются без правок, не собирается `cluster` из-за ошибки в naga 0.19.
4. Тот же агент проверил и твой путь: один HLSL-исходник через DXC 1.9 даёт и SPIR-V, и DXIL. DX11 (FXC, модель 5.1) в описанных им опытах не проверялся.

Вопрос: оставляем HLSL, как ты решил 22 октября, или принимаем рекомендацию агентов (WGSL остаётся единственным исходником)? Разница. HLSL: 14 готовых шейдеров нужно один раз переписать (автоперевод через naga даёт черновик), зато исходник собирают инструменты Microsoft для всех трёх API (DXC для Vulkan и DX12, FXC для DX11). WGSL: переписывать ничего не нужно, но DX11 и DX12 зависят от качества автоперевода в сторонней библиотеке naga (она уже дала одну ошибку на `cluster`), а DX11 пока не проверен. В обоих случаях исходник один, «втрое меньше работы», как ты и хотел. Мой вариант — оставить HLSL, как решено; но решать тебе, потому что агенты располагают данными, которых не было 22 октября (шейдеры на WGSL уже есть).

Пока решение не принято, их шейдеры на WGSL остаются рабочими (мой вывод); а проверка «хватит ли модели 5.1» откладывается до первых шейдеров на HLSL или до проверки DX11 на переводе. Остаётся одна проверка, а не вопрос к пользователю: хватит ли подмножества модели 5.1 для всего запланированного (Forward+, каскадные тени, океан, SSR, TAA) — выяснится на первых шейдерах. Если не хватит, варианты (мои, не обсуждались): отдельные упрощённые версии этих шейдеров для DX11 либо отказ от DX11 — вернёмся к вопросу тогда.
