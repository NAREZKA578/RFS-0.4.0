# Анализ сектора рендера и RHI

**Дата:** 2026-10-09
**Автор:** AGENT-SBF1
**Зона:** `src/render/`, `src/rhi/`, `examples/`
**Объём:** 185 файлов, 44 414 строк

---

## 1. Главное, что нужно понять про этот сектор

Рендер **выглядит** готовым. В нём есть семь пассов, граф с топологической
сортировкой, ресурсный менеджер, кэши пайплайнов, система па��тиц, вода, тени,
материалы. Всё это компилируется, проходит clippy и покрыто типами.

**Реально исполняет GPU-работы ровно один пасс — `geometry`.** Остальные шесть
создают ресурсы и не рисуют. Это не «недоделано понемногу»: у пяти из шести
пайплайн **не создаётся вовсе**, и в коде это написано прямым текстом.

Отсюда главная опасность сектора, и она же объясняет, почему здесь столько
истории: **состояние «написано, но не включено» не ломает ни одну сборку и не
ломает ни один тест.** Подсистема может быть отполирована до блеска, не
подключившись, и всё будет зелёным. Это уже стоило работы двоим — с
`pub mod ui;`, который выпал из объявления, и с `theme.rs`, который был
никем не заявлен, 400 строк кода и два теста, которые не выполнялись.

Вывод, который стоит держать: **в рендере зелёная сборка не является
доказательством того, что кадр рисуется.** Доказательство — пиксели,
прочитанные из буфера.

|---|---|---|---|---|---|
| `geometry.rs` | 866 | да, через `Device` | **да** | **да** | да (`examples/cube`) |
| `ui.rs` | 373 | да, через `UiRenderer` | да | да, но см. §5 | да (`examples/ui_spike`) |
| `gbuffer.rs` | 413 | частично | **нет** | нет | **нет** |
| `shadow.rs` | 236 | частично | **нет** | нет | **нет** |
| `lighting.rs` | 423 | частично | **нет** | нет | **нет** |
| `transparent.rs` | 386 | частично | нет, `HashMap` пуст | нет | **нет** |
| `water.rs` | 509 | частично | **нет** | нет | **нет** |

Отдельно, вне графа: постпроцесс, 1069 строк семь файлов — ресурсы настоящие,
пайплайнов нет (§2.1).

**Ровно один пасс доходит до GPU и рисует.** `add_pass` во всём репозитории
вызывается из шести мест: `examples/cube.rs` (`GeometryPass`),
`examples/ui_spike.rs` (`UIPass`), и четыре раза в тестах графа. Ни
`GBufferPass`, ни `ShadowPass`, ни `LightingPass`, ни `TransparentPass`, ни
`WaterPass` не инстанцируются нигде, кроме собственных файлов и реэкспортов в
`passes/mod.rs`.

Доказательства по каждому:

**`gbuffer.rs`** — пайплайн не создаётся, строка 356:

```rust
// Create pipeline
// This would require shader modules to be loaded
// For now, we'll leave it as None and create it when shaders are available
```

`_pipeline` инициализируется `None` и ни разу не присваивается. Хуже: пять
вложений создаются настоящими текстурами, а **render pass и фреймбуфер — нет**.
`gbuffer.rs:274` вызывает `crate::rhi::RenderPass::new(...)`, а это
CPU-заглушка (`src/rhi/command/pass/render.rs:113`), которая не доходит до
бэкенда. `execute` пишет `begin_render_pass` + `end_render_pass` и всё.

**`shadow.rs:178`** — тот же комментарий, `_depth_pipeline` остаётся `None`.
Тени не получают ни матриц света, ни геометрии.

**`lighting.rs`** — три поля пайплайна (`_pipeline`, `_ssao_pipeline`,
`_ssr_pipeline`) объявлены и не заполнены. Три текстуры создаются через
`Texture::new` — то есть **без GPU-аллокации**. `resize` — пустая заглушка с
комментарием `// Implementation similar to GBufferPass`.

**`transparent.rs:353-361`** — тело цикла по объектам состоит из *одного*
поиска в `self.pipelines`, а `self.pipelines` — `HashMap::new()`, который никогда
не заполняется. То есть даже `bind_pipeline` не срабатывает.

**`water.rs`** — самый явный файл. `update_waves` (строка 499) целиком:

```rust
fn update_waves(&mut self, context: &RenderContext) {
    let _time = context.total_time.as_secs_f32();
}
```

`render_reflection` и `render_refraction` не пишут ничего. Восемь полей с
префиксом `_` объявлены и не используются.

### 2.1 Постпроцесс — подсистема, которую я сначала пропустил

```rust
if let Some(pipeline) = &self.bright_pass_pipeline {
```

То есть код записи написан, и он выполнится, как только появится пайплайн. Это

это решение изменилось, либо эффект написан сверх плана и должен быть убран. Это
вопрос к владельцу, не к агенту.

## 3. Структурная причина: пассы никогда не инициализируются

Это важнее, чем сами заглушки, потому что объясняет, почему добавление пасса в
граф ничего не даёт.

`RenderGraph::initialize` (`graph.rs:67-191`) добавляет десять ресурсов
и заканчивается комментарием:

```rust
// Create and add default passes
// Note: Actual pass creation will be done in the initialize method
// after all systems are set up
```

Он **не вызывает** `node.initialize(device, context)`. Метод
`RenderPassNode::initialize` (`node.rs:121`) и `RenderPassNode::resize`
(`node.rs:126`) **не имеют ни одного вызова во всём репозитории**. У
`RenderGraph` вообще нет метода `resize`.

Следствие: тело `initialize` каждого пасса — мёртвый код. Даже если добавить
`GBufferPass` в граф, его текстуры не создадутся, а `execute` выйдет рано по
`framebuffer.is_none()`.

**Исправлено, №311.** `RenderGraph::initialize` теперь вызывает `initialize` у
каждого узла, добавлен `RenderGraph::resize`, и он вызывается из `Renderer::resize`.
Три теста с негативным контролем. Признак, который был на виду и не читался:
параметр устройства в `initialize` назывался `_device` и не использовался.

Второй структурный дефект того же рода: `GraphResource::create`
(`resource.rs:120`) **никем не вызывается**. Все десять ресурсов графа созданы
через `GraphResource::new`, то есть как дескрипторы без объектов:
`texture: None, buffer: None, view: None`. Отсюда, например, что
`lighting.rs:396-400` итерирует десять ресурсов и привязывает ноль вьюпортов.

Есть и живая ошибка рядом: `resource.rs:187`

```rust
if self.usage != ResourceUsage::RenderTarget
```

сравнивает **весь** набор битов с одним битом, поэтому ресурс, объявленный
`RenderTarget | Sampled`, никогда не получит view.

### 3.1 Прибор против этого класса, №304

Выше зафиксировано: состояние «написано и не подключено» не ломает ни одну
сборку. Поэтому добавлен прибор, спрашивающий не «тест ли зелёный», а
«выполнялась ли эта строка».

**Уровень исполнения.** В `RenderGraph` — счётчик на узел, растущий в циклах
`execute` и `record`, то есть в единственной точке, через которую проходит любой
пасс. Наружу: `pass_execution_counts`, `never_executed`, `execution_summary`.

Счётчик намеренно на графе, а не на узле: поле в `RenderPassNode` ломает все
структурные литералы — я это попробовал и сломал `examples/cube.rs` на первой
сборке, то есть повторил ровно ту ловушку, которую сегодня же объяснял коллеге
как «не делай так». И не в глобальной переменной: cargo запускает тесты потоками
в одном процессе, и глобальный счётник смешивал бы результаты.

**Уровень объявления.** Тест
`Tool/client_tests/tests/pass_reachability.rs::every_declared_pass_is_instantiated_somewhere`
читает исходники и требует, чтобы каждый тип пасса создавался вне собственного
файла. Allowlist с обязательной причиной у каждой записи, плюс проверка
устаревания: если заявленный неподключённым пасс начнёт создаваться, тест падает
и требует убрать запись — иначе список долгов протухает молча.

Сейчас allowlist называет пять: `GBufferPass`, `ShadowPass`, `LightingPass`,
`TransparentPass`, `WaterPass`. Каждая причина — конкретная, а не «не сделано».

**Чего прибор не делает.** Он не измеряет покрытие строк и не заменяет его.
`llvm-cov` на этой машине недоступен: компонент `llvm-tools` числится
установленным, бинарники отсутствуют, принудительная переустановка их не
создаёт, и файлы исчезают сразу после установки — вероятно, их снимает защита.
Бороться с антивирусом я не стал. Прибор построен так, чтобы работать без новых
инструментов; покрытие осталось бы более строгим инструментом, и если слой
разрешит его установку — это отдельная задача.

## 4. Граф даёт порядок, но не даёт барьеры

Топологическая сортировка через Канна (`graph.rs:194-232`) работает и
наблюдаема — `execution_order` доступен и `execute`/`record` идут по нему.

Но `ResourceUsage` — полноценный битсет с объединением, пересечением,
разностью и шестью тестами — **не потребляется нигде**. Поиск по `graph.rs`
слов `barrier`, `transition`, `read`, `write` даёт ноль совпадений.

Конкретно: поля `resource_name` и `usage` у `PassDependency` не читаются ни
где, кроме цикла сортировки; `node.outputs` возвращается наружу и не
учитывается при исполнении. Нет ни анализа опасностей, ни read-after-write,
ни вставки барьеров между пассами, ни версионирования ресурсов.

Практическое следствие: **переводы лейаутов целиком в руках каждого пасса**,
поэтому `gbuffer.rs:183-239` выписывает все десять `initial_layout`/
`final_layout` руками. Это не стилистика — это признак того, что подсистемы
планирования ресурсов нет.

`execute` при этом не декоративен: он создаёт пул, начинает буфер, пишет
команды, завершает и отправляет, и предупреждает, если записано ноль команд.
Это и была правка №209, и она настоящая.

## 5. Окно UI и просьба AGENT-SBF2

Коллега нашёл, что оконный путь не может **начать** render pass. Дамп порядка
команд через `UI_SPIKE_DUMP=1`:

```
SetViewport, BindGraphicsPipeline, BindDescriptorSets,
BindVertexBuffers, BindIndexBuffer, SetScissor, DrawIndexed
```

Ни `BeginRenderPass`, ни `EndRenderPass`. Отсюда `VUID-vkCmdDrawIndexed-renderpass`
и `VUID-VkPresentInfoKHR-pImageIndices-01430` — картинка свопчейна на present
остаётся `UNDEFINED`.

Причина: `UiRenderTarget` несёт сырые `u64`, и `TextureView` из `u64` не
собрать — нужен `Texture`, которого у UI нет.

**Это исправлено (№298)** — см. §8. Но правка не «три строки»: отсутствовала
точка входа в RHI, потому что `Texture` и `TextureView` не имеют `as_raw`.

## 6. Дефект класса «размер из resolution»

Это отдельный класс, и он не закрыт.

Правильный источник размера — **дескриптор фреймбуфера**, потому что он
гарантированно совпадает с размером вложений, и он же используется в
`record.rs` при отсутствии `render_area`. Отсюда viewport, scissor и вложения
согласованы по построению, а не по совпадению двух независимых вычислений.

`geometry.rs:662-671` сделано правильно: дескриптор фреймбуфера →
`presentation_extent` → `resolution` как запасной.

**Сломаны остальные пять.** Каждый берёт `context.resolution` напрямую:

| файл | строки | что sizing'ает |
|---|---|---|
| `gbuffer.rs` | 106-107, 383-384 | пять текстур + render area |
| `lighting.rs` | 143-144, 373-374 | три текстуры + render area |
| `transparent.rs` | 146-147, 267-268 | две текстуры + render area, viewport, scissor |
| `water.rs` | 197-198, 374-375 | две текстуры + render area, viewport, scissor |
| `graph.rs` | 80-81 … 183-184 | **18 мест**, все десять ресурсов |
| `postprocess/bloom.rs` | в `initialize` | текстуры яркого прохода и пингпонга |

`shadow.rs` — единственный **из пассов**, кто этого класса избежал: он
использует `self.config.resolution`, потому что карта теней по размеру окна и не
масштабируется.

Не проявляется по одной причине: единственный реально исполняемый пасс — тот,
кто сделан правильно. Как только заработает второй — проявится. На машине с
масштабом 125% окно логическое 1280×720 даёт физическое 1600×900, и `resolution`
врёт на каждом из этих мест.

## 7. Что ещё лежит в секторе

Из 148 записей реестра, относящихся к рендеру и RHI, ровно **одна** имеет
статус «Не сделано» — №291 (`CopyBufferToTexture`, ждёт решения владельца API).

Остальные помечены «Исправлен», «Не исправлено» или «Исправлен частично».
Здесь стоит быть осторожным: коллега отдельно проверял реестр и нашёл пять
записей, которые врали — код был давно исправлен, а статус остался
«не исправлен». **Статус «Исправлен» в этом файле нельзя принимать за
доказательство без сверки по строкам.** Пример: §3 выше показывает, что
«исправленные» текстуры `lighting` не имеют GPU-аллокации вообще.

Также вне реестра и не оценено:

- **`RenderStats`** (`core/stats.rs`, 138 строк) реализован полностью и **не
  вызывается ниоткуда**. Единственные упоминания — его определение и
  реэкспорт.
- **`renderer.rs:550-552`** — `if shadow_changed { }` с пустым телом. Переменная
  вычисляется и выбрасывается.
- **`context.rs:158`** — `self.render_target = ...` закомментировано, поле
  `render_target` не присваивается никогда.
- **`include_bytes!` в `src/render/passes/ui.rs:45,51`** тянет в чужой воркспейс
  `Tool/client_tests/assets/shaders/`. Проверено поиском по всему `src/`: это
  единственные **фактические** вызовы, которые так делают. Остальные вхождения
  слова — комментарии (`geometry.rs:224`, `rhi/ui/shaders.rs:9`,
  `rhi/ui/renderer.rs:633`), и там как раз сказано правильное правило: «вызывающий
  встраивает `.spv`». `ui.rs` нарушает это правило, которое сам же и
  декларирует строкой выше. Коллега отметил это в самом первом письме, и я на
  это тогда не ответил.

## 8. Что сделано в этом заходе

Четыре просьбы коллеги, все адресованные моей зоне, все с проверкой.

**№297 — пропуск слоя валидации больше не молчит.** `instance.rs` печатает
сообщение, если слой запрошен, но недоступен: называет слой, говорит, что
валидация выключена и что «чистый прогон тогда ничего не проверял», показывает
доступные слои, указывает на `VK_LAYER_PATH`. Плюс `rhi::validation_layer_active()`.

**№298 — `presentation_texture_views`.** Добавлены `Device::adopt_texture` и
`Texture::adopt`, заворачивающие чужой хендл в типизированный `Texture`.
Образ остаётся за `Swapchain` — в трек-лист он не попадает, иначе двойное
уничтожение.

Здесь я сначала ошибся: `create_texture_view` **отслеживает** создаваемый view,
так что три view на образ свопчейна завели утечку в 3 объекта на пересоздание.
Самопроверка ресайза показала это сразу — 23 → 26 → 29 → 32. Исправлено
освобождением через `release_many`; 8 шагов держат 17 объектов.

**№299 — `download_texture` берёт лейаут из трекинга.** Флаг usage говорит, для
чего образ *может* использоваться, а не где он есть. В записи отслеживаемого
объекта добавлено `layout`; `submit_commands` обновляет его по барьерам отправки
— после того, как список команд известен, а не внутри переводчика, иначе трекер
менялся бы при неудачной отправке.

**Предел честно назван:** границы render pass трекер не видит. Перевод через
`initial_layout`/`final_layout` пасса трекер не обновляет. Сделать это точным —
значит вести учёт ещё и render pass'ов.

**№300 — `GeometryPassState::with_resources` вместо `#[derive(Default)]`.**
Отклонение от просьбы коллеги, осознанное: пять ресурсов структуры намеренно не
имеют `Default`, потому что дефолтный пайплайн или layout — это ресурс без
бэкенда, ровно та ловушка, что уже стоила работы двоим.

## 10. Порядок работы дальше

**1. №282 — кольцо буферов. Самая крупная оставшаяся работа.**

Требует N command buffer'ов и N fence'ов (`RhiConfig::max_frames_in_flight`
уже есть, значение 2) и **два** семафора на образ свопчейна: `imageAvailable`
сигналит acquire и ждёт submit, `renderFinished` сигналит submit и ждёт
present. Один семафор на оба нельзя — сигнал один, а ждать его надо дважды.

Симптомы, которые это закрывает, зафиксированы обоими и наблюдались вживую:
индекс образа уходил на 2 и там оставался; окно UI пустое; кадр
рендерился в образ, уже отданный предыдущим present. CPU сейчас прижат к
GPU, потому что `submit_recorded` ждёт fence на каждый кадр, и это следствие
одного общего command buffer.

Начинать это стоит отдельным заходом с проверкой после каждого шага: путь
кадра сейчас чист, и ломать его ради частичной реализации хуже.

**2. Дать `RenderGraph` вызов `initialize` у пассов и `resize`.** Без этого
любой новый пасс не создаст ресурсы. Это правка на несколько строк, но она
переводит шесть заглушек из «невозможно включить» в «можно включить и
довести».

**3. Вызвать `GraphResource::create`.** Тогда ресурсы графа получат объекты,
и `dependency.resource_name`/`usage` станут осмысленными.

**4. GBuffer.** Первым из пассов, потому что от него зависят тени и освещение.
Требует настоящего MRT-шейдера, настоящего пайплайна и перевода
`create_render_pass` на путь, доходящий до бэкенда.

**5. Перевести остальные пассы на дескриптор фреймбуфера** (§6) — до того,
как они начнут исполняться, иначе каждый внесёт свой экран на 125%.

**6. Решить №291** — три варианта расписаны в реестре.

## 11. Одно замечание о самом анализе

Этот документ описывает состояние на момент 2026-10-09 и снимается чтением
кода, а не прогоном каждого пасса. Утверждения вида «не рисует» сделаны по
коду: пайплайн не создаётся, тело цикла пустое, `update_waves` читает время в
переменную и не делает ничего. Прогоном это не подтверждено — пассы не
подключены, и подключать их ради проверки этого утверждения значило бы начать
п.4 раньше п.2.

Что подтверждено прогоном: всё, что касается `geometry` — 0 утечек, 0 VUID,
стабильный счётчик на ресайзах. Остальное — чтение кода.
